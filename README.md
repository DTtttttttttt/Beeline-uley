# Планировщик выездов инженеров

Кейс «Билайн Бизнес», ЛЦТ 2026. Панель диспетчера, которая распределяет заявки по бригадам на один день, строит маршруты, показывает их на карте, объясняет решения и перестраивает план по событиям в течение дня.

## Проверить за 5 минут

Что нажать в интерфейсе, какой модуль за это отвечает и какой тест это охраняет. Код — от
`backend/app/`, если путь не начинается со `scripts/` (это `backend/scripts/`), тесты —
`backend/tests/`. Экран — после «Новый датасет» → «Использовать
демо-набор» → «Выбрать» у любого варианта.

## Запуск

Нужны Docker с Docker Compose (память Docker — около 8 ГБ), около 3 ГБ на диске и ключ 2ГИС
(подойдёт бесплатный демо-ключ). Valhalla обязательна: она считает время в пути и рисует маршруты
по дорогам. Её тайлы собираются один раз, это около 20 минут.

Готовый `.env` с рабочими настройками будет приложен к дополнительным материалам.

```bash
cp .env.example .env
# вписать ключ 2ГИС в DGIS_API_KEY

# 1. Дороги: выгрузка OpenStreetMap, из неё вырезаются Москва и область
curl -L -o cfd.osm.pbf https://download.geofabrik.de/russia/central-fed-district-latest.osm.pbf
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD:/data" debian:12-slim sh -c "apt-get update -qq && apt-get install -y -qq osmium-tool && osmium extract -b 35.1,54.2,40.3,57.0 /data/cfd.osm.pbf -o /data/valhalla/custom_files/moscow-region.osm.pbf"
rm cfd.osm.pbf

# 2. Тайлы Valhalla: ждём, пока сервер ответит
cp valhalla/custom_files/valhalla.json valhalla.json.bak
docker compose --profile valhalla up -d valhalla
until curl -sf http://localhost:8002/status > /dev/null; do sleep 30; done
mv -f valhalla.json.bak valhalla/custom_files/valhalla.json
docker compose --profile valhalla restart valhalla

# 3. Остальные сервисы
docker compose --profile valhalla up -d --build
curl http://localhost:8000/api/health   # mongo и valhalla должны быть "ok"
```

Когда всё поднялось, откройте `http://localhost:3000`. При первом входе откроется окно «Новый
датасет». Выберите в нём заявки и состав бригад и нажмите «Использовать демо-набор» (свой файл —
на вкладке загрузки, кнопка «Загрузить и рассчитать»). Демо-наборы бэкенд после первого старта
сам просчитывает в фоне, по паре за раз (около 2 минут на пару, 12 пар — около 25 минут, строки
«Прогрев кэша решений» в логе). После этого
варианты открываются за секунды; свой файл считается около минуты. Затем
выберите нужный вариант кнопкой «Выбрать». После открытия первого рассчитанного плана короткий
тур покажет основные элементы интерфейса; его можно пройти или пропустить.

Ссылку клиента на оценку заявки строит `PUBLIC_BASE_URL` (по умолчанию `http://localhost:3000`).
Чтобы открыть её с телефона в той же сети, укажите адрес машины в трёх местах:
`PUBLIC_BASE_URL=http://192.168.1.5:3000`, `NUXT_PUBLIC_API_BASE=http://192.168.1.5:8000` и
`CORS_ORIGINS=["http://192.168.1.5:3000"]`. Для своего домена — то же с его адресом; если фронтенд
и API на одном домене, прокси перед ними отправляет `/api/` на порт 8000, остальное — на 3000.
`RATING_SECRET` без него случайный на запуск, и выданные ссылки перестают работать после
перезапуска бэкенда; в контейнер он не передаётся — задаётся при запуске `uvicorn` из `.env`.

Остановить: `docker compose --profile valhalla down`. Следующий запуск — `docker compose --profile
valhalla up -d`, тайлы собирать заново не нужно.

## Что умеет

- **Два плана на одних данных:** базовый, строго по алгоритму ТЗ, и оптимизированный (Google OR-Tools).
  Оптимизация учитывает, что авария важнее любой другой заявки, затем стремится выполнить больше заявок,
  задействовать меньше бригад и проехать меньше километров. Базовый план выдаётся только если он не хуже.
- **Ограничения:** навык, транспорт, оборудование и инструменты, окно заявки, смена бригады, время
  в пути, количество оборудования, которое бригада может взять с собой на день. Каждый план заново
  пересчитывается отдельной независимой проверкой.
- **Объяснения:** почему заявка досталась этой бригаде и почему не подошли остальные, почему маршрут
  именно такой, а для неназначенной заявки — причина, пометка «перенести на следующий день» и «Что
  поможет»: ближайшее окно, в которое её возьмут, недостающее оборудование, транспорт, ещё одна
  бригада или продлённая смена. Каждое средство проверено расчётом; окно переносится и бригада
  добавляется одной кнопкой. Учебный демо-состав «Нехватка» (5 инженеров) показывает это нагляднее
  всего.
- **События в течение дня:** новая или срочная заявка, авария, недоступность бригады, выход новой
  бригады, отмена, перенос, правка заявки или бригады, фиксация факта выполнения. Уже начатая работа не
  пересматривается. Отмену и перенос можно применить сразу к нескольким заявкам. Видно, что изменилось
  и каким клиентам нужно сообщить новое время. Перед применением окно «Пересчёт дня» показывает
  варианты: встроить заявку в свободное время, пересчитать остаток дня или весь день. Для каждого видно,
  сколько заявок останется без назначения, сколько инженеров задействовано и какой путь — было →
  стало, а сам вариант — на карте; рекомендуемый отмечен. У аварии перед ним — окно «Кто поедет на аварию?»: едущего к обычной заявке разворачивают по дороге, работающий доделывает и едет; по умолчанию едет тот, кто прибудет раньше, можно выбрать другого. Варианты считаются параллельно (`SOLVER_WORKERS` в `.env`, по умолчанию 3
  процесса), применяется только выбранный.
- **Ассистент:** фраза обычным текстом («Соколов заболел с 13:00», «перенеси заявку 74198 на завтра»,
  «отмени все заявки в Кашире», «новая авария на Волгоградском 128 к5») или вопрос («почему заявка
  74198 не у Соколова?», «кто свободен?»). Умеет одним предложением отменить или перенести несколько
  заявок — по номерам, инженеру или населённому пункту, не затрагивая уже начатые и закрытые, — и по
  просьбе пересчитать весь день с начала. Правит инженеров и заявки («у Соколова смена до 20:00»,
  «пересади Никитина на машину», «окно заявки 74198 с 14 до 16») и показывает было → станет; новый
  тип или адрес заявки открывает её карточку, нового инженера — форму добавления, а «покажи план на
  15:00» переводит время дня по кнопке. Стартовую точку инженера не меняет. Помнит контекст
  диалога и уточнения; «Новый чат» очищает переписку. Новую заявку вне Москвы и Московской области не предлагает. На просьбы не по плану
  (код, рецепты, тексты) отвечает отказом; если кому-то плохо — советует звонить 103 или 112.
  Отдаёт заявку другому инженеру («отдай 74198 Соколову») и отвечает на «что будет, если…»
  («…Соколов заболеет в 13:00?», «…отдать 74198 Попову?»): считает это черновиком и показывает,
  сколько станет заявок, бригад и километров и кто останется без исполнителя; план не меняется,
  пока не нажать «Применить».
  К сообщению можно приложить до трёх файлов CSV, JSON или TXT до 1 МБ (скрепка или перетащить на
  окно): ассистент отвечает по ним, сверяет с планом и предлагает добавить заявку из файла. Файл
  формата загрузки он узнаёт («56 заявок формата загрузки»). XLSX и картинки не читает.

  Фразу разбирает YandexGPT, но ничего не решает: событие или заявка остаются предложением, которое
  применяет диспетчер, а ограничения по-прежнему проверяет расчёт. Кнопка ассистента находится на
  карте. Нужны `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` в `.env` (см. `.env.example`), без них кнопки нет.
  Там же можно настроить модель, тайм-аут, лимит ответа и глубину рассуждений. Адреса заявок и
  содержимое приложенных файлов при этом уходят в Yandex Cloud; текст файла хранится в базе сутки.
- **Интерфейс:** отдельные сценарии знакомства для компьютера и телефона — с шагами про рейтинг,
  скорость, сложность объекта и «Кто поедет на аварию», — подсказки у значков (наведение на
  компьютере, нажатие на телефоне), адаптивная карта и списки, а для долгих операций — полоса прогресса с оценкой оставшегося времени. Формы заранее проверяют
  обязательные поля, координаты, смены и окна заявок и подсвечивают поля, которые нужно исправить;
  повторные действия на время расчёта блокируются.
- **Сложность объекта (доп. ТЗ):** длительность работы считается по объекту — этаж без лифта,
  квартиры в подъезде, тип здания, подъезд к дому — условиям работы (гигабит, повторный выезд,
  прокладка кабеля, сверление) и скорости инженера. Объект и условия правятся в окнах «Информация о
  здании» и «Условия работы»; блок «Почему по плану дольше норматива? 70 → 94 мин · +24 мин» в
  форме и карточке раскладывает добавку по причинам в минутах, в «Метриках» — сколько добавила
  сложность и сравнение с расчётом по нормативу. Сложность учитывается всегда.
- **Скорость инженера (доп. ТЗ):** сервер ведёт часы дня (`POST /api/plans/{id}/clock`): работа,
  чья скрытая фактическая длительность истекла, закрывается сама, затянувшаяся перестраивает остаток
  дня только при конфликте — переставляет заявки у того же инженера, отдаёт другому или помечает
  «не удалось после задержки». Часы идут вместе с проигрыванием дня и настенным временем: досрочно
  закрытый блок гантта сразу короче, затянувшийся растёт по минутам, а перестроенный план даёт
  уведомление «План перестроен из-за задержки заявки №…» со ссылкой на «План обновлён». После каждой
  выполненной заявки скорость инженера плавно обновляется в профиле — бейдж «↘ 12%» (медленнее
  нормы) или жёлтый «↗ 8%» (быстрее) у имени и блок «Почему работает медленнее нормы?» в карточке; у кандидатов видно, сколько заявка займёт у каждого. Когда
  кончились все смены, кнопка «Итоги дня» в шапке открывает работу по плану и по факту и скорость
  было → стало (`GET /api/plans/{id}/day-summary`). Перемотка на вечер догоняет день одним вызовом
  часов: все закрытия по порядку, версиями.
- **Рейтинг инженеров (доп. ТЗ):** у инженера в списке — бейдж «★ 4,8» (от 4,5 жёлтый) и
  «из резерва»; в карточке — окно «Отзывы» с распределением оценок и изменением за
  месяц. Выполненную заявку диспетчер оценивает из её карточки или строки списка — оценка уходит
  тому, кто сделал работу, и сразу видна в списке. Клиенту — QR со ссылкой на страницу оценки.
  В своём файле рейтинг бригады задаётся колонками `rating` и `reviewsCount` (в JSON — полем
  `rating`); у примеров загрузки он уже есть.
- **Начало дня из дома (доп. ТЗ):** в карточке инженера — галочка «Начинает рабочий день из дома» и
  стартовая точка адресом. Вместе со стартом галочка меняет оборудование: из офиса — всё, из дома — то, что
  лежит дома. На карте у каждого инженера домик в его цвете, линия маршрута идёт от старта. В
  «Метриках» — «Дорога до первой заявки: в среднем N мин».
- **Сверх обязательного:** сравнение восьми вариантов расчёта (среди них «Рейтинг в приоритете»: работа выполняется лучшими по рейтингу, с инженерами из резерва), метрики и графики, ручное переназначение
  с проверкой ограничений, прогноз вероятности опоздания, перемотка дня назад и проигрывание дня (нажатие на
  время в шапке: полоса со шкалой и скоростью от «реального времени» до 20 мин/с, инженеры едут по
  маршрутам, статусы идут за временем), готовые демо-наборы
  (три участка × три состава бригад, плюс учебный состав), загрузка своего набора в JSON или CSV.
- **Выгрузка:** кнопка «Выгрузить» в шапке сохраняет показанную версию плана файлом CSV, который
  Excel открывает двойным щелчком: сводка, маршруты по бригадам со статусами и неназначенные с
  причинами (`GET /api/plans/{id}/export.csv`). Основной вариант — «Аварии в приоритете», он отмечен
  в окне «Варианты плана»; базовый посчитан дословно по п. 2.3 ТЗ.

## Замеры

Числа ниже считает скрипт, руками их никто не правит: `python scripts/measure.py` (из `backend/`)
переписывает таблицы, `python scripts/measure.py --check` падает, если README с ними разошёлся.
Valhalla и Mongo скрипту не нужны: таблицы переездов демо-наборов посчитаны заранее. Поиск
OR-Tools останавливает предел числа решений, а не часы, поэтому на любой машине выходят те же
числа. Считается на настройках по умолчанию, `.env` на них не влияет. Времени расчёта здесь
нет: оно зависит от машины.

Смены — по ответу организаторов: 2/2 с 10:00 до 22:00 и 5/2 с 09:00 до 18:00. Обед — час
в окне 13:00–16:00 между работами (блоки 79, 82): после работы, если за ней есть ещё работа и час
помещается в окно.

Длительность работы — с учётом сложности объекта (этаж без лифта, тип здания, подъезд к дому и
другие факторы, `docs/data.md`), как в демо-наборах по умолчанию. Таблица «по нормативу» ниже —
тот же встроенный набор без неё.

Авария — заявка с типом BK «Глобальная проблема». По ответу организаторов аварию задаёт поле HD,
но решение по BK переделывать не требуется. По HD аварий меньше: на «Востоке» 3 из 8, на
«Югоцентре» ни одной, на «Юго-востоке» те же 12. Остальные «Глобальные проблемы» становятся
локальными заявками на 30 минут. Таблицы ниже посчитаны по BK. Замер по HD: `python
scripts/prepare_data.py --seed 1 --emergency-by hd` (ключ 2ГИС не нужен — адреса в кэше), затем
`python scripts/measure.py`. Команда переписывает наборы в `data/` и таблицы README, поэтому после
замера их нужно вернуть: `git restore data/ README.md`. Иначе приложение на следующем старте
будет планировать по HD.
